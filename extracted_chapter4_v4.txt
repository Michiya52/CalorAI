First, the multi-source logging approach — photo, barcode, manual search, and composite building — means the system is usable in real-world meal scenarios that don't fit a single logging pattern. Third, the chatbot's streamed response rendering made the AI interaction feel more natural than waiting for a full response to appear. The quick-prompt chips reduced the cognitive load of formulating a question from scratch, which made the chatbot feel more accessible to testers who had not previously used a dietary AI assistant.                  5.3.8 Limitations              Four limitations were identified during testing. The most significant is the variability of food recognition accuracy across dish categories. Dishes with distinctive visual presentation — like Roti Canai or Char Kway Teow — were identified reliably. Mixed dishes, stews, and rice-based dishes with similar appearances were less consistent. This is a known         constraint of vision-based food identification noted in the literature (Min et al., 2025) and is mitigated by the user confirmation step before any entry is saved.             Second, the photo logging pipeline and the barcode scanner both require a live connection, since they depend on the Gemini API and barcode lookups respectively. Manual search is more resilient than initially assumed: alongside MyFCD and SG Focos, the app bundles two additional local JSON datasets (backed_foods.json and backed_my_foods.json) as assets, which appear to provide offline-capable packaged/branded food coverage rather than relying solely on a live USDA connection. The photo and barcode paths remain the two features most exposed to poor connectivity.             Third, the chatbot's personalization is limited to the current session's meal data. It does not yet analyze patterns across multiple days, which means it cannot notice that a user consistently over-eats on weekends or skips breakfast. The SharedPreferences session history preserves conversation continuity but is not used to train or adjust recommendations over time.             Fourth, the evaluation sample was small: five testers across UAT and a limited dish set for the accuracy tests. The findings are directionally useful but not sufficient to generalize performance across all Malaysian and regional cuisine or all user demographics. A larger validation study would be needed before CalorAI could be deployed as a public health tool.             Fifth, the weight tracking feature is incomplete. The WeightLog model, the weight_logs Firestore sub-collection, and its security rules are all implemented, but no screen in the current build reads from or writes to that collection. Weight is only captured as a single overwritable field on the user's profile rather than a proper dated history. This is a backend-ready, frontend-missing gap rather than a design flaw, and is addressed as a recommendation in Chapter 6.             Sixth, the Firestore security rules for the /foods collection allow any authenticated user to write to it, relying on the convention that writes are only performed through the Firebase Admin SDK rather than enforcing that restriction at the rules level. In the current single-developer prototype this has not caused any issue, but it is a latent security gap that         should be tightened before any public release, for example by restricting writes to a specific admin role or moving all food database updates to a Cloud Function.            Seventh, code verification also surfaced two pieces of leftover or abandoned code worth noting for completeness. The WeightLog model and its associated Firestore methods (saveWeightLog, getWeightLogs) are fully implemented but never called by any screen, consistent with the incomplete weight-tracking gap already discussed above. Separately, the project still contains Firebase Data Connect boilerplate (lib/dataconnect_generated, including files like create_movie.dart and add_review.dart) — default placeholder code generated by Firebase tooling that is entirely unrelated to calorie tracking and should be removed for code cleanliness before any future submission or deployment.                  5.3.9 Project Objective Achievement              The overall results show that CalorAI's core objectives were achieved in functional form. Chapter 6: Conclusion                   6.1 Critical Evaluation              The project aimed to develop CalorAI, a calorie tracking application for Malaysian and Southeast Asian cuisine that uses AI image recognition to reduce manual logging friction and a conversational chatbot to provide personalized dietary guidance. The completed prototype fulfils this aim across all its core feature areas: user authentication and profile management, AI-powered photo meal logging cross-referenced against regional food databases, barcode scanning for packaged goods, composite meal building for home-cooked recipes, an OpenRouter-powered conversational assistant, and a personal progress dashboard.             The application addresses the core problems identified during the investigation phase. Manual logging friction is reduced through the photo-based workflow, barcode scanner, and composite meal builder, which together cover the majority of real-world logging scenarios without forcing the user into a single rigid input method. The localization gap is addressed by grounding dish recognition in MyFCD and SG Focos before falling back to AI estimates, and by giving users a database toggle so they can choose which source to search. The passive-logbook problem is addressed by the chatbot, which uses the user's actual goal, calorie target, and today's meal log to generate specific, grounded suggestions rather than generic advice.             From a technical standpoint, CalorAI shows a working integration between Flutter, Firebase, two separate AI providers, and three food data sources, coordinated through a clean provider-based state layer. Building the chatbot on OpenRouter rather than directly on Gemini was a deliberate cost and reliability decision: it gives access to a capable free-tier model for the primary conversational path while keeping Gemini available as a fallback if OpenRouter is unreachable. The clear separation between providers, services, and screens made it possible to add the barcode scanner and composite meal builder after the initial IR scope without restructuring the rest of the app.             The evidence chain from the investigation through to implementation holds together reasonably well. The literature and the survey both pointed to the same three gaps, and the implemented system addresses them directly. Source labelling, user confirmation         before saving, and the multi-database search toggle are all features that trace back to specific findings from the earlier research phase rather than being added arbitrarily.                  6.2 Limitation              Several limitations were identified over the course of the project. The most significant is the variability of AI-based food recognition across dish categories. Distinctive dishes are identified reliably, but visually similar dishes — different noodle soups, mixed rice combinations, and regional variants of the same base dish — are harder for the model to separate reliably from a single image. This is consistent with known limitations of vision-based food recognition in the wider literature and is one reason the confirmation step before saving an entry is not optional.             A second limitation is network dependency. Three of the four logging paths — photo, barcode, and USDA-backed manual search — require an active internet connection. Only the local MyFCD and SG Focos JSON assets work offline. Users in areas with unreliable connectivity, which is not uncommon in parts of Malaysia and the wider region, would experience degraded functionality for the AI-powered features specifically.             A third limitation is that the chatbot's personalization only extends to the current day's data. It does not build a longitudinal picture of the user's eating patterns over weeks or months, so it cannot flag habits like consistently skipping breakfast or over-eating on weekends. Session history is preserved locally for continuity within a conversation, but it isn't used to adjust future recommendations.             A fourth limitation concerns evaluation scope. UAT involved five testers and the accuracy testing covered a limited set of dishes. This is appropriate for a single-developer prototype within one semester, but the results should be read as directional rather than conclusive. A production deployment would need substantially larger testing before any claims about accuracy or usability could be generalized.             A fifth limitation is that removing Open Food Facts, while it simplified the codebase, did leave USDA as the sole source for some packaged product categories that Open Food Facts may have covered better, particularly for products manufactured or sold primarily in Southeast Asia rather than the US.                   6.3 Recommendation              Several directions are recommended for future development. First, expanding the test dataset for AI recognition accuracy would give a clearer picture of which dish categories need targeted prompt refinement. A structured benchmark set covering common dishes across MyFCD's food groups and SG Focos' categories, tested under varied lighting and presentation conditions, would let future iterations measure improvement objectively rather than relying on anecdotal testing.             Second, building longitudinal awareness into the chatbot would move it from a same-day assistant toward genuine ongoing coaching. Storing a rolling summary of the past 7 to 14 days of meal data and feeding relevant patterns into the system prompt — without requiring the model to process the full raw history every time — would let it notice trends like inconsistent breakfast logging or a pattern of high-calorie weekend meals.             Third, reintroducing a broader packaged-goods data source or supplementing USDA with a regional packaged goods database would improve barcode scan coverage for products common in Malaysia and Singapore that may not appear reliably in a US-centric database. This is a lower priority than the accuracy and personalization improvements but would close a known coverage gap.             Fourth, expanding UAT to a larger and more demographically varied group, including older users and users with less smartphone familiarity, would validate whether the current interface choices generalize beyond the five testers involved so far. This is particularly relevant for the onboarding and profile setup flow, which assumes a reasonable degree of comfort with mobile app conventions.             Fifth, testing offline resilience more thoroughly and potentially caching a larger subset of USDA data locally would reduce the practical impact of the network dependency limitation, particularly for users who rely primarily on manual search rather than photo logging.             Sixth, exploring wearable integration for activity data would allow the calorie target to adjust based on actual daily activity rather than a fixed activity-level multiplier set once during profile setup, bringing the personalization closer to what the chatbot promises conversationally.              Seventh, and most immediately actionable, is building the missing weight tracking interface. Since the WeightLog model, Firestore sub-collection, security rules, and service methods (saveWeightLog and getWeightLogs) already exist, this would be a comparatively small addition: a screen to log a dated weight entry and a chart to display the trend, both wired into infrastructure that is already sitting unused. This is a natural next feature given how much of it is already built.
